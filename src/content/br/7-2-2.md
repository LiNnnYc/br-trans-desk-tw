> **CRL and CRL entry extensions**

> Table: CRL Extensions

表：CRL 延伸欄位

| **延伸欄位** | **必要性** | **Critical** | **說明** |
| ---- | - | - | ----- |
| `authorityKeyIdentifier` | 應（MUST）| 否 | 參見第 7.1.2.11.1 節 |
| `CRLNumber` | 應（MUST）| 否 | **應（MUST）**包含一個大於等於零（0）且小於 2¹⁵⁹ 的整數（INTEGER），且為嚴格遞增序列 |
| `IssuingDistributionPoint` | * | 是 | 參見第 7.2.2.1 節「CRL 簽發分發點」 |
| 其他任何延伸欄位 | 不建議（NOT RECOMMENDED）| - | - |

> Table: revokedCertificates Component

表：revokedCertificates 元件

| **元件** | **必要性** | **說明** |
| ---- | - | ----- |
| `serialNumber` | 應（MUST）| **應（MUST）**與廢止憑證中的 `serialNumber` 逐位元組完全相同 |
| `revocationDate` | 應（MUST）| 通常為廢止發生的日期與時間。倒填日期（backdating）之許可情形見本表後附注 |
| `crlEntryExtensions` | * | 詳見「crlEntryExtensions 元件」表 |

> **Note**: The CA SHOULD update the revocation date in a CRL entry when it is determined that the private key of the Certificate was compromised prior to the revocation date that is indicated in the CRL entry for that Certificate. Backdating the revocationDate field is an exception to best practice described in [RFC 5280, Section 5.3.2](https://datatracker.ietf.org/doc/html/rfc5280#section-5.3.2); however, these requirements specify the use of the revocationDate field to support TLS implementations that process the revocationDate field as the date when the Certificate is first considered to be compromised.

**注意**：若確定憑證私密金鑰（Private Key）在 CRL 條目所載廢止日期之前即已洩漏（compromise），CA **宜（SHOULD）**更新 CRL 條目中的廢止日期。倒填 `revocationDate` 欄位是 RFC 5280 第 5.3.2 節所述最佳實務的例外；然而，本文件要求使用 `revocationDate` 欄位，以支援將 `revocationDate` 作為憑證首次被認定遭洩漏之日期的 TLS 實作。

> Table: crlEntryExtensions Component

表：crlEntryExtensions 元件

| **CRL 條目延伸欄位** | **必要性** | **說明** |
| --- | -- | ----- |
| `reasonCode` | * | 若存在（OID 2.5.29.21），**不得（MUST NOT）**標記為 critical，且**應（MUST）**指出廢止該憑證之最適當原因。<br><br>除非 CRL 條目所對應的憑證在技術上不具備簽發憑證能力，且符合以下情形之一，否則**應（MUST）**存在：1）廢止日期早於 2023-07-15 且受本文件要求規範之用戶憑證，或 2）廢止原因（即 `reasonCode`）為 unspecified (0)。<br><br>詳見「CRLReasons」表 |
| 其他任何值 | 不建議（NOT RECOMMENDED）| - |

> Table: CRLReasons

表：CRLReasons

| **RFC 5280 reasonCode** | **RFC 5280 reasonCode 值** | **說明** |
| --- | - | ------ |
| unspecified | 0 | 以省略 reasonCode 表示。若 CRL 條目所對應憑證在技術上不具備簽發憑證能力，**應（MUST）**省略，除非該條目屬於 2023-07-15 前廢止且受本文件要求規範之用戶憑證 |
| keyCompromise | 1 | 表示已知或疑似用戶私密金鑰（Private Key）已遭洩漏 |
| affiliationChanged | 3 | 表示憑證中主體（Subject）名稱或其他主體身分資訊（Subject Identity Information）已變更，但無理由懷疑憑證私密金鑰已遭洩漏 |
| superseded | 4 | 表示憑證因以下原因被取代：用戶已請求新憑證；CA 有合理證據認為不宜繼續信賴憑證中任一完全吻合網域名稱（FQDN）或 IP 位址之網域授權或控管驗證；或 CA 因法遵問題（如憑證不符合本文件要求或 CA 之 CP 或 CPS）廢止憑證 |
| cessationOfOperation | 5 | 表示持有該憑證的網站於憑證效期屆滿前停止運作，或用戶於憑證效期屆滿前不再擁有或控管憑證中的網域名稱（Domain Name） |
| certificateHold | 6 | 若 CRL 條目屬於下列情形之一，**不得（MUST NOT）**納入：1）受本文件要求規範的憑證；或 2）不受本文件要求規範但符合 A）於 2020-09-30 當日或之後簽發，或 B）`notBefore` 為 2020-09-30 當日或之後的憑證 |
| privilegeWithdrawn | 9 | 表示用戶方發生違規情事，且未導致金鑰洩漏（keyCompromise），例如憑證用戶在憑證請求中提供誤導性資訊，或未履行用戶協議或使用條款中之重要義務 |

> The Subscriber Agreement, or an online resource referenced therein, MUST inform Subscribers about the revocation reason options listed above and provide explanation about when to choose each option. Tools that the CA provides to the Subscriber MUST allow for these options to be easily specified when the Subscriber requests revocation of their Certificate, with the default value being that no revocation reason is provided (i.e. the default corresponds to the CRLReason "unspecified (0)" which results in no reasonCode extension being provided in the CRL).

用戶協議或其中所引用的線上資源，**應（MUST）**告知用戶上述廢止原因選項，並說明各選項的適用情形。CA 提供給用戶的工具，**應（MUST）**允許用戶在請求廢止憑證時輕易指定上述選項，且預設值為不提供廢止原因（即預設對應 CRLReason「unspecified (0)」，使 CRL 中不包含 reasonCode 延伸欄位）。

> The privilegeWithdrawn reasonCode SHOULD NOT be made available to the Subscriber as a revocation reason option, because the use of this reasonCode is determined by the CA and not the Subscriber.

`privilegeWithdrawn` reasonCode **不宜（SHOULD NOT）**作為可供用戶選擇的廢止原因選項，因為此 reasonCode 的使用由 CA 決定，而非用戶。

> When a CA obtains verifiable evidence of Key Compromise for a Certificate whose CRL entry does not contain a reasonCode extension or has a reasonCode extension with a non-keyCompromise reason, the CA SHOULD update the CRL entry to enter keyCompromise as the CRLReason in the reasonCode extension.

若 CA 取得金鑰洩漏（Key Compromise）之可查證證據，且該憑證的 CRL 條目不含 `reasonCode` 延伸欄位、或其 `reasonCode` 延伸欄位非為 `keyCompromise` 原因，CA **宜（SHOULD）**更新 CRL 條目，將 `reasonCode` 延伸欄位中的 CRLReason 改為 `keyCompromise`。
